## Задача 1 — восстановление JPEG со спутника

Вход — текстовый лог приёмника SDRangel (`map_Rx.txt`). Пакет 74 байта:

| Байты | Поле |
|---|---|
| 0–4 | заголовок `01 02 03 04 05` |
| 5–8 | синхрослово `31 6F 6B 6F` (только пакеты изображения) |
| 9–12 | смещение в файле, **little-endian** |
| 13–14 | номер файла (`06 00`) |
| 15–68 | 54 байта данных |
| 69–71 | резерв (нули) |
| 72–73 | CRC-16 |

Формат лога: строка `[ЧЧ:ММ:СС] ✓ CRC OK` либо `CRC FAIL`, под ней HEX-строка пакета.

Конвейер: оставить `CRC OK` → hex→bytes → проверить синхрослово → `int.from_bytes(b[9:13], "little")` → `buf[offset:offset+54] = b[15:69]` (повторы перезаписывают, так и задумано) → после укладки всех кусков принудительно `buf[0:2] = b"\xFF\xD8"` (передатчик намеренно портит первые два байта JPEG) → запись в бинарном режиме.

Подводные камни: `CRC FAIL` пропускать; big-endian для смещения даёт абсурдные значения; `FF D8` восстанавливать **после** укладки кусков, иначе затрётся.

Запуск из корня репозитория (лог — артефакт, поэтому лежит в `samples/` и не коммитится):

```bash
python3 decode_jpeg.py samples/map_Rx.txt samples/image.jpg
```

Без аргументов скрипт ищет лог в текущей папке (`спутник бурмалдутник.txt`, `map_Rx.txt`, `samples/map_Rx.txt`) и пишет `image.jpg`.

## Задача 2 — БПЛА + OpenCV, поиск кратчайшего маршрута

- Нет кадра/конфига → exit 2 и сообщение на русском, без трейсбека. Пустой кадр, шум, `None` → пустой результат, exit 0.
- Пока `px_per_meter: null`, длина выводится в пикселях; после калибровки — в метрах.
- Опасный маршрут на поле пока заглушка (синий №3); спутниковая картинка задаёт его парой меток (см. ниже).
- Длина — по 1-px скелету (морфологический скелет + Zhang-Suen, без `cv2.ximgproc`), диагональные шаги взвешены `sqrt(2)`. Не заменять на `cv2.arcLength` контура: он меряет периметр и завышает длину толстых линий.
- При появлении кадров: положить в `samples/frames/`, откалибровать `hsv_ranges`, `px_per_meter`, `min_area_px`, уточнить `dangerous`.
- ArUco на спутниковом снимке `samples/image.jpg`: словарь `DICT_4X4_50`, id 0 и 2. Детектор (`mars/aruco.py`) не падает на `None`/пустом кадре, неизвестный словарь → `ValueError`. Для реальных кадров словарь и `marker_size_m` перепроверить на поле.
- Опасный маршрут со спутника — цепочка белых стрелок между метками 0 и 2 (3 стрелки, ~140 px), детектор `mars/arrow_routes.py`. На полевом кадре 1920×2560 тот же детектор находит 3 маршрута: `0->4` (13 стрелок), `0->3` (8), `0->2` (3). Маршрут привязан к паре меток, поэтому несколько маршрутов в кадре не смешиваются; исключать опасный маршрут на поле по этой паре.
- Детектор стрелок работает по форме, а не по цвету: контуры на Canny-краях плюс маски красного/синего. Поддержаны белые, красные и синие стрелки разного размера; пороги заданы в долях стороны маркера, поэтому код не зависит от разрешения. Белая краска принимается только при совпадении края блоба с печатным контуром и локальном контрасте (тень стрелки и светлое пятно пола отбрасываются). Цепочки строятся графом соседей с обрезкой «коротких замыканий»; цепочка, у которой промежуточная стрелка прижата к краю кадра, не считается маршрутом — маршрут уходит за кадр только у метки.
- План параллельной работы команды (владение файлами, ветки, фазы): `docs/stage2-plan.md`.

### Пульт (TUI)

```bash
python3 -m pip install "pioneer-sdk2>=0.11"   # только на ноутбуке, до Wi-Fi дрона
python3 drone_tui.py --dry-run                 # интерфейс без железа
python3 drone_tui.py                           # ноутбук в Wi-Fi дрона
python3 drone_tui.py --local                   # на борту
```

- Пакет называется `pioneer_sdk2` (не `pioneer_sdk`): `Pioneer(tcp="10.42.0.1:20556")`, RTSP-камера `10.42.0.1:8554`, `Camera(camera_ip=...)`. `Pioneer()` на неудачном TCP вызывает `exit()`, поэтому `DroneLink` ловит `SystemExit` и печатает русское сообщение.
- Управление — body-fixed скорости (`set_manual_speed_body_fixed`), `yaw_rate` в рад/с. Импульс 0.35 с: отпущенная клавиша обнуляет ось, потеря терминала не оставляет дрон лететь.
- `X` — выход с автоматической посадкой; `--max-altitude` (3 м) блокирует набор высоты.
- `ServoCamera` ходит через Unix-сокет `/tmp/servo.sock`, поэтому наклон камеры работает только в `--local` на борту; с ноутбука — поток, фото и полёт.
- `set_angle()` не читает реальный угол: `True` значит лишь «датаграмма ушла в сокет». Пульт шлёт команду с приоритетом `HIGH`, повторяет её и удерживает раз в секунду; диагностика без TUI — `python3 drone_tui.py --local --servo-test`.
- Углы в пульте физические: `0°` — горизонт, `−90°` — вниз. Шкала SDK сдвинута: горизонт `+30`, вниз `−80`; пересчёт линейный по двум точкам (`ServoScale`), калибровка флагами `--servo-zero` и `--servo-down`. `[`/`]` ведут камеру в крайние положения (вниз/горизонт), а не шагами. Угол уходит на борт **целым** числом: дробный payload борт игнорирует.
- Журнал `logs/flight_*.jsonl`, фото `photos/` — артефакты, в git не попадают. Подробности: `docs/drone-tui.md`.

### Фото-миссия

```bash
python3 photo_mission.py --dry-run                # последовательность без железа
python3 photo_mission.py --local                  # вниз, 2.7 м, точка (0.5, 0.5), фото, посадка
python3 photo_mission.py --local --altitude 3.0   # ключевой параметр — высота
python3 photo_mission.py --local --target-x 1.0 --target-y 1.0
```

- Последовательность: наклон камеры `--tilt` (по умолчанию −90°), взлёт, набор `--altitude` над точкой взлёта закрытым контуром по LPS (fallback — барометр), перелёт в `--target-x`/`--target-y` (по умолчанию 0.5/0.5 м от точки взлёта) с удержанием высоты, пауза `--settle`, фото с повторами, снижение до `--landing-height` и полная посадка в этой точке.
- Перелёт тоже закрытый контур по LPS: координаты точки взлёта запоминаются после взлёта, тело-фиксированные скорости поворачиваются на текущий yaw; допуск `--move-tolerance`, скорость `--move-speed`, таймаут `--move-timeout`.
- Наклон сервопривода доступен только в `--local`; без него скрипт предупреждает, пишет `tilt_unavailable` в журнал и продолжает миссию.
- Наклон удерживается повтором раз в секунду. Шаги (`mission_start`, `takeoff_reference`, `climb_progress`, `move_progress`, `move_done`, `photo`, `descent_done`, `land`, `mission_complete`) и ошибки — в `logs/flight_*.jsonl`.
- Ошибка или Ctrl+C → аварийная посадка, код возврата 1/130; нет связи — 2. Полный список флагов прокомментирован в шапке `photo_mission.py`.

### Дрон через второй ноут (кабель) — рабочий вариант

Второй ноут, подключённый к точке дрона, **пропадает из домашней сети**: у него один радиоблок. Поэтому путь к нему — только Ethernet-кабель напрямую между ноутами. У этой машины порт `enp8s0` свободен (`carrier=0`, профиль `Проводное подключение 1`).

```
[эта машина] --кабель 192.168.50.0/24-- [второй ноут] --Wi-Fi 5 ГГц-- [дрон 10.42.0.1]
```

- На втором ноуте: `sudo tools/second_laptop_setup.sh --key "<публичный ключ>"` — ставит и включает sshd, создаёт профиль `v2m-link` (`192.168.50.2/24`, `ipv4.never-default yes`, чтобы кабель не забирал дефолт у Wi-Fi дрона), добавляет ключ.
- На этой машине: `tools/remote_drone.sh status` → `forward` → `stop`, `pull` для кадров.
- `forward` поднимает локальные туннели `9999/9090/22` на `10.42.0.1`. После этого IDE дрона открывается как `http://localhost:9999/?folder=/home/pioneermini/workspace`, Jupyter — `http://localhost:9090/`. IP-маршрутизацию через второй ноут настраивать не нужно, VPN и домашний Wi-Fi не затрагиваются.
- **Проверка связи — только через `ip route get`.** VPN `happ-xray` отвечает на ICMP по *любому* адресу: при выдернутом кабеле `ping 192.168.50.2` даёт ответы с `172.19.0.1`. Поэтому `status` проверяет `carrier=1` и что интерфейс маршрута совпадает с Ethernet-устройством, и лишь потом пингует.
- Ключ называется `~/.ssh/id_ed22519` (опечатка в имени), поэтому ssh не подхватывает его сам — передавай `-i ~/.ssh/id_ed22519`.
- `sudo` на этой машине требует пароль: шаги установки IP на кабеле и запуск sshd выполняет пользователь.
